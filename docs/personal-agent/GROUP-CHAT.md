# Bot 群聊 · 机制设计与实现

> v1（2026-11-03）：基于本仓库代码实读 + 本轮落地的改动。
> 配套代码：`src/client/personal/room-trigger.ts`（谁接话）、`src/client/personal/room-queue.ts`（成员排队）、`src/host/personal/room-context.ts`（群历史与场地登记）。
> 配套测试：`scripts/test-room-trigger.mjs`（`npm run test:room-trigger`）。

## 一句话结论

**群聊的价值不是「多个 Bot 一起说话」，而是「用户只描述一次意图，由系统决定谁来做」——所以群聊的第一职责是分派入口，触发必须是可预测的判定，而不是让模型猜。**

---

## 一、群聊在这个产品里到底解决什么

按价值排序，只有第一条是刚需，其余是它的副产品：

| 价值 | 用户原话大致长什么样 | 为什么单聊替代不了 |
|---|---|---|
| **分派入口**（刚需） | 「帮我把这份周报整理一下，顺便让设计那边看一眼」 | 单聊要用户自己判断「这事该找谁」，再把同一段话复制两遍。群聊把「该找谁」交给判定规则 |
| **多视角评审** | 「你们三个各说一版方案」 | 单聊要串行三轮、每轮用户手动转述上一轮结论 |
| **流水线协作** | 「A 先出稿，B 再配图」 | 交接发生在 Bot 之间，用户只看结果 |
| **可围观纪要** | 「我自己看他们讨论」 | 单聊里没有「别人说话」这件事 |

**明确不做的三件事**（它们看着像群聊，实际都是反模式）：

- **抢答**：每句话所有 Bot 都回。成本是 N 倍而不是 1 倍，且用户没要求。
- **私聊替代**：把群当「多人聊天室」用，用户仍然一次只找一个人。那用单聊更清楚。
- **角色扮演**：Bot 之间互相客套、复述对方结论。产出为零，token 照扣。

## 二、谁接话：四档判定（命中即停）

判定在 `resolveRoomTrigger()` 里，**纯函数、不依赖 React 与宿主**，所以能被测试完整覆盖。顺序不能反——前三档是用户**已经表达出来**的确定性意图，只有第四档是系统猜：

| 档 | 触发条件 | 谁回复 | 判定依据 |
|---|---|---|---|
| ① 广播 | `@所有人` / `@全体成员` / `@all` / `@everyone` | 全员 | 广播词必须**紧跟 `@`**；正文里出现「所有人」三个字不算 |
| ② 点名 | `@名字`（全角 `＠` 同样认） | 只叫被点名的，按点名出现顺序去重 | 结构化匹配，最长名字优先 |
| ③ 引用 | 用户点了某条 Bot 消息的「引用」 | 只叫被引用的那个 | 点「回复」是界面上最明确的一次「这条是问你」，不靠中文推断 |
| ④ 委托 | `让 / 请 / 叫 / 找 / 交给 / 派给 / 由` **紧邻**成员名 | 只叫被委托的那个 | 委托词与名字之间只允许隔一个空格或标点 |
| ⑤ 兜底 | 以上都没有 | 群主（`memberIds[0]`） | 不叫全员——用户没要求 |

顺序里的两处取舍：**`@` 压过引用**（用户既点了引用又在正文 @ 了别人时，@ 是更晚的一次选择），**引用压过委托**（UI 动作比文本推断确定）。被引用的人已经退群时按「没引用」处理，不报错。

### 为什么不反过来：先让模型判断「他大概想找谁」

那等于把确定信息丢掉再用猜测重建。`@` 是结构化信号，模型判断是概率信号；有确定信号时用概率信号，只会让同一个动作的结果在两次之间不一致。

### 边界情况（每一条都有回归测试钉住）

| 输入 | 结果 | 为什么 |
|---|---|---|
| `我记得小墨说过…` | 不叫小墨，群主兜底 | 正文随口提到名字 ≠ 点名。这是原实现 `value.includes(bot.name)` 的 bug 本体 |
| `user@example.com` | 不命中成员 `example.com` | `@` 前后紧贴词字符时不算点名 |
| `@2x 的图` | 不命中以数字开头的成员 | `@` 后紧跟 ASCII 数字视为倍率写法 |
| `@小墨助手`，成员同时有「小墨」 | 只命中「小墨助手」 | 最长优先，避免短名抢先匹配 |
| `让小墨的同事看一下` | 不算委托 | 名字后紧跟「的」是领属/转述，不是委托 |
| `我让小墨的同事看，让小墨自己来定` | 命中小墨 | 逐个匹配位置验边界，不被第一处转述挡住 |
| `@ 小墨`（隔空格） | 不算点名 | `@` 与名字之间不允许空格 |
| 群里 0 个成员 | `responders` 为空 | 调用方必须提示，不能静默丢消息 |

### 一次最多编排 3 位成员

每位成员都是一次**完整的模型推理**加一整段上下文。超出上限时：

- 被挤掉的成员进 `overflow`，前端弹一条 toast 说清「谁这次没接」，并建议「分开 @，或让群主转派」；
- 原来这里是 `mentioned.slice(0, 2)` 静默截断——第 3 个被 `@` 的人永远不回复，用户只会以为它坏了。

## 三、群聊的会话与上下文

### 现在怎么做（方案 2：单会话 + 群历史注入）

每个 Bot 仍只有**一个终身会话** `pa-bot-v2-<botId>`。群聊回合时，前端把**本群**最近 20 条消息（含其他成员发言，已排除本轮这条）随请求体的 `history` 一起带上，宿主用 `buildRoomContextBlock()` 拼成一段 developer 消息，在用户消息之前注入。

- **只带本群**：别的群的消息是另一种场地的事，混进来就是串场地。
- **必须带名字**：群里模型要分清哪句是自己说的、哪句是别人说的；私聊不带（多一层噪音）。
- **硬上限 6000 字符 / 单条 600 字符**，超限时从**最近的**发言往回装，并在开头写明「更早的消息已省略」。
- **块头要说明「不是用户二次提问」**：这段紧挨着本轮用户消息投进去，不点明来源的话模型容易把历史逐条重新回答。
- 失败一律吞掉——群上下文是增强项，坏了不能连累对话。

### 为什么没做方案 1（per-member-per-room 会话）

方案 1 是「session id 加 `-<roomId>`，一个 Bot 在每个群一份独立历史」。它多解决一个「场地隔离」问题，但代价是：每个「Bot × 群」组合一个常驻 agent、压缩各算各的、记忆提取会重复、现有历史没有干净的迁移分法。

看过两个参照实现之后，结论是**先不做**：

- **Grok Bot** 明确不做场地隔离——它说「群聊里你的 Bot 能用你在私聊告诉它的事」，要保密靠用户口头指示。
- **DS Bot**（`_tmp/ds-bot-ref`）做了方案 1，但它同时有三件配套才成立：`read_own_chat`（可搜自己私聊的所有历史段）、群级共享记忆（`groups/<群id>/`）、上下文管家（判断压缩还是换段 + 交接笔记）。缺任何一件，方案 1 都会变成「既互相看不见、又各自失忆」的最差版本。

等真的出现「它把我私聊的话带到客户群了」这类抱怨，再付这个代价。

### 仍然缺的

| 缺口 | 后果 |
|---|---|
| 记忆引擎的 owner 只有 `work` 与 `bot:<id>` | 没有 `room:<id>`，「这个群的约定」只能靠每次注入的群历史维持，Bot 不会主动记住 |
| 群历史是**事件流**不是**记忆** | 20 条之后的内容就看不到了；Bot 也不能把「群里的规矩」沉淀下来 |
| 群历史只覆盖 20 条 | 更早的群消息看不到；Bot 也不能把「群里的规矩」沉淀下来（要有群记忆才解决） |

## 四、本轮已落地的修复

| 问题 | 原来的表现 | 现在的做法 |
|---|---|---|
| 群里的审批卡 / 问答卡不出现 | 卡片由宿主异步发，只知道 `botId`，于是落进私聊；群里那条回复永远等不到应答（聊天内审批 `CHAT_TIMEOUT_MS = 0`，根本不会过期） | 回合入口 `setBotRoom(botId, body.roomId)` 登记本回合所属群，卡片发布时补进事件的 `roomId`；私聊回合即删除登记（否则后台例行任务的卡会被塞进上一轮那个群） |
| `room.modelMode` 是死字段 | 设置里能选、能保存、README 也写了，但宿主读的仍是各自 `bot.model`，一轮回复都不会按它走 | 回合开始时按群设置解析出 `unifiedModel`，覆盖进请求体的 `bot.model`。在**回合开始时**定下，跑到一半改设置也不会让同一条回复由两个模型写 |
| 清空私聊连带删掉群消息 | 清空按 `botId`/`senderId` 过滤，群消息也有这两个字段 | 过滤改成「保留所有带 `roomId` 的消息」，清空只作用于私聊 |
| 正在看的群也累计未读 | 用户盯着群里几条回复，侧栏冒出一个红色角标说他「有 3 条未读」 | `selectedRoomId === room.id` 时不加未读 |
| 停止后排期中的成员无声消失 | 按停止只取消了已启动的轮次，还没 `later` 到点的成员静默不发 | 统计被取消的排期数并提示「另有 N 位还没开始接话的成员已取消」 |
| 群成员互相看不见 | 群消息进不了模型上下文：「三个成员各说一版方案」实际是三个互不知情的单聊 | 群聊回合把本群最近 20 条消息随 `history` 带上，宿主注入成 developer 消息（见第三节） |
| 点「引用」回复某个 Bot 却由群主接话 | 引用只是 UI 上的引用条，判定时被完全忽略 | 判定加一档：引用了谁就只叫谁（见第二节） |

## 五、群聊里刻意保留的约束

- **默认只有一个发言人**：多出来的发言人必须由用户显式调用（`@` / 委托 / 广播）。
- **严格串行**：每个成员等**上一位把这一轮说完**再启动，不并发、也不固定错峰。
  - 判据抽在 `src/client/personal/room-queue.ts` 的 `shouldStartNext()`（纯函数、有真值表测试）。核心不是「上一位在不在跑」，而是「上一位**启动过没有**」——第三位第一次检查时，第二位可能还排在第一位后面没启动，用「不在运行中」判「已说完」就会让两位同时开口。
  - 运行时判据用 `runningReplyTurnsRef` 里「上一位在本群是否还有活着的轮次」——和停止键共用同一个真相，不会出现「点了停止还在等一个永不结束的 promise」。
  - 超时 **180 秒**兜底：某一位卡住（宿主没回、工具跑飞）不能把后面所有人一起冻住。到点直接开始，宁可看不到完整前文，也不让群里半天没动静。
  - 为什么不能固定错峰：一轮回复要几十秒，第二个成员若在 1 秒后启动，第一个的正文还在流式生成（消息仍是 `pending`），它既看不到前文，「多视角评审」就退化成三个人各自回答同一段背景。
- **Bot 自己发的消息不触发任何回复**：只有 `role === 'user'` 的群消息走判定，避免 Bot 之间无限互相触发。
- **群主兜底但不代劳**：群主接住之后如果确实需要别人，它自己会用 `coordinate_bots` 派活（只有主 Bot 挂这个工具）。

## 六、待办（按优先级）

1. **群级记忆**：记忆引擎加 `room:<id>` owner，让「这个群的约定」能被 Bot 主动记住，而不是每轮靠 20 条群历史续命。
2. **群里不发起审批**：现在审批卡能被送回群（修的是「气泡永远转圈」），但 Grok Bot 的做法是这类操作根本不在群里发起——需要审批就转私聊并说清楚。我们更可能该往那个方向收。
3. **输入框的 `@` 补全**：现在 `Composer` 只有手动点「@ 提及」按钮插名字，没有输入 `@` 触发的成员选择弹层。
4. **`@all` 的二次确认**：广播是一次 N 倍的推理开销，误触发代价高。
